# 처음 쓰는 사용자의 준비와 배포

## 배포 추천: Cloudflare를 먼저 제안

**기본 추천은 Cloudflare 한 곳에 발표 화면·서버·필요한 저장소를 묶는 경로다.** Workers Static Assets로 화면을, Worker로 API를 운영하고 필요할 때만 Durable Objects(공유 상태/실시간 연결), D1(구조화된 기록), R2(파일)를 같은 Cloudflare 계정에서 연결할 수 있다. 별도 호스팅·DB 서비스 계정을 여러 개 연결하는 부담을 줄이는 것이 우선 추천 이유다. 모든 저장소를 처음부터 만들지 않는다. 한 계정이어도 리소스 생성·바인딩·권한·Secret·비용 조건은 확인해야 하며 ‘연결 한 번이면 모든 설정이 자동 완료’라고 설명하지 않는다.

선택 순서:

1. 사용자가 이미 배포 서비스를 지정했거나 기존 서비스를 유지하라고 했으면 그 지시를 우선한다.
2. 그 외에는 **Cloudflare를 첫 추천으로 보여준다.** 현재 제공된 플러그인/게시 도구와 인증된 실행 경로를 확인한다. 적합한 Cloudflare 도구가 있으면 사용하고, 없으면 현재 환경에 맞는 Wrangler 또는 정적 Drop 경로를 설명한다. 플러그인이 있는 척하거나 일반 가입/로그인을 플러그인 연결이라고 부르지 않는다. 인증이 아직 없다는 이유만으로 Cloudflare 추천을 자동 생략하지 않는다.
3. Cloudflare 사용을 원하지 않거나 필요한 기능/실행 도구·계정 정책·비용 조건이 맞지 않으면 **대안 하나를 추가 추천**한다. 대안은 가능한 한 이미 연결된 플러그인을 사용하고, 추가 계정 수가 적은 구성을 고른다. 별도 연결이 필요하면 실제 플러그인을 검색해 안내하며 설치·연결·인증·배포 기능의 가용성을 구분한다.
4. 배포 요청과 대상이 정해지면 같은 범위에서 진행한다. 공개 배포를 원하지 않으면 로컬 발표 HTML/소스를 제공한다. 기능을 유지할 수 없는 대안에서는 무엇이 빠지는지 설명하고 임의로 제거하지 않는다.

| 상황 | 우선 제안 | Cloudflare를 사용하지 않을 때의 예시 |
|---|---|---|
| 일반 발표·로컬 조작·영상 | Cloudflare 정적 배포 | 실제 배포 도구가 제공된 Netlify/Vercel 등 |
| 설문·Q&A·진행자와 참가자 동기화 | Workers와 필요한 Cloudflare 공유 상태/저장소 | 기존 Node 서버를 실행할 Railway 등, 또는 사용자가 이미 쓰는 실시간 백엔드 |
| 기존 DB/서버를 유지해야 함 | 사용자 지정 기존 구성 우선, 필요한 경우 Cloudflare 화면 연결 | 기존 연결된 호스팅/백엔드 재사용 |

Supabase 같은 별도 백엔드는 기존 사용/특정 필요가 있을 때 선택한다. Cloudflare가 가능한데도 관성적으로 ‘호스팅 한 곳 + DB 한 곳’의 추가 가입을 기본으로 요구하지 않는다. 이 표는 추천 기준이며 모든 provider의 배포 어댑터가 동봉돼 있다는 뜻이 아니다. 선택한 도구의 실제 생성·업로드·환경 설정·상태 확인 기능과 공개 검증 경로를 확인한다. ‘플러그인 설치됨’만으로 계정 인증이나 자동 배포 성공을 주장하지 않는다.

**Drop과 서버 배포는 구분한다.** Cloudflare Drop은 정적 사이트 공유 경로이고, 커스텀 서버 코드·저장소까지 함께 배포하는 경로가 아니다. 실시간 기능이면 해당 Worker와 리소스 설정/검증을 추가한다. MP4가 내장된 큰 HTML은 배포 경로의 파일 한도를 확인하고, 필요하면 프로젝트 영상 파일/선택한 파일 저장소를 사용한다. 편집본 저장이 공개 사이트에 자동 업로드되는 것으로 설명하지 않는다.

근거: [Workers Static Assets](https://developers.cloudflare.com/workers/static-assets/), [리소스 바인딩](https://developers.cloudflare.com/workers/runtime-apis/bindings/), [Cloudflare Drop](https://www.cloudflare.com/drop/). 서비스별 지원/도구/비용은 추천 시 현재 상태를 확인한다.

## 도구 발견 → 필요한 순간 동의

우선 현재 환경에 제공된 브라우저/게시 도구와 기존 프로젝트 의존성을 확인한다. 처음부터 Node·Playwright·Wrangler를 전부 설치하지 않는다. 프로젝트의 `node harness/harness.mjs doctor`는 읽기 전용이며 도구 상태와 질문 예시를 JSON으로 출력한다. 이 명령은 계정 상태를 확인하거나 패키지를 다운로드하지 않는다.

사용자에게 실제로 묻는다. 스크립트의 `--consent`는 이미 받은 답을 실행 단계에 전달하는 인자이며 사용자 응답을 대신하지 않는다. 상위 실행 환경의 승인/설치 정책을 우선한다.

- **브라우저 검사 필요**: “화면 잘림과 버튼 동작을 자동으로 검사하려면 Playwright와 Chromium이 필요해요. 이 프로젝트에 패키지와 검사 브라우저를 설치할까요? [설치하고 검사 / 설치 없이 진행]”
- **Cloudflare를 선택했고 Wrangler가 필요한 경우**: “이 경로로 배포하려면 Wrangler가 필요해요. 이 프로젝트에 설치할까요? 계정 가입·로그인은 별도예요. [설치하고 배포 준비 / 다른 배포 방법]” 이미 가능한 게시 도구가 있으면 중복 설치를 요구하지 않는다.
- **Node 없음**: “제작·검사 도구를 실행할 Node.js가 필요해요. 설치를 도와드릴까요? [설치 진행 / 파일로만 받기]” OS와 설치 범위를 확인한 후 공식 설치 경로를 안내/지원한다. 관리자 권한이나 시스템 설정을 임의로 바꾸지 않는다. 기본 하네스는 Node 22 이상을 사용한다.

기존 승인과 설치를 재사용한다. 거절 시 로컬에서 열 수 있는 `public/index.html`과 에셋을 제공하고 미실행 검사를 적는다. 정적 분석만으로 실제 브라우저 검증 완료를 주장하지 않는다. 브라우저 도구가 이미 제공되면 그것을 이용할 수 있고 Playwright를 중복 설치할 필요는 없다. 이때는 해당 도구의 관찰 증거를 남기고, 동봉 자동 게이트를 쓸 경우 실행 가능한 Playwright 연결을 확보한다. JSON의 `passed` 값을 손으로 바꿔 우회하지 않는다.

동의 후 프로젝트에서 실행:

```sh
node harness/harness.mjs setup --tool browser --consent install-browser
node harness/harness.mjs setup --tool deploy --consent install-deploy
```

브라우저 설치는 프로젝트의 Playwright와 사용자 캐시의 Chromium, 배포 설치는 프로젝트의 Wrangler만 대상으로 한다. 전역 npm 설치나 sudo를 기본으로 사용하지 않는다. 필요한 도구만 설치한다. OS 필수 라이브러리 부족 등 실패가 있으면 정확한 원인을 알리고 설치 범위를 넓히기 전에 확인한다.

이미 제공된 의존성을 재사용하려면 `WORKSHOP_PLAYWRIGHT_MODULE`에 Playwright 모듈 진입 파일, `WORKSHOP_WRANGLER_CLI`에 Wrangler CLI JS 파일의 경로를 환경변수로 전달할 수 있다. 경로는 현재 환경에서 확인하고 배포 파일/공유 스킬에 개인 절대 경로를 하드코딩하지 않는다.

## 로컬 편집 요청함

Node 22 이상이 있으면 `npm run dev`만으로 로컬 요청함을 쓸 수 있다. 추가 패키지·Playwright·Wrangler·계정·AI API 키는 이 전달 경로의 요건이 아니다. 브라우저 수정 요청을 같은 프로젝트 폴더에 저장하고 파일 접근 에이전트가 읽는다. 별도 Python 정적 서버에는 이 API가 없으므로 표준 개발 서버로 실행한다. [로컬 요청함](local-editor-inbox.md)에서 사용법과 실제 검증 경계를 확인한다. 127.0.0.1 전용 서버를 외부에 노출하지 않으며, 공개 정적 배포에는 요청함이 포함되지 않는다.

## 계정 연결

도구 설치와 계정 가입은 다르다. Cloudflare 경로를 선택했고 대상 계정이 없으면 사용자가 브라우저에서 Cloudflare에 가입·로그인하도록 안내한다. 가입을 원하지 않으면 위 기준에 따라 다른 배포 경로를 추천한다. 비밀번호/OTP/API 키를 채팅으로 받지 않는다. 로그인은 사용자 동작이며 설치 허용으로 대신하지 않는다.

기존 인증을 확인할 때는 기존 Wrangler의 `whoami`를 사용한다. 새 로그인은 준비된 CLI로 `wrangler login`을 실행하고 사용자가 브라우저에서 인증한다. 로그인/정책 동의가 끝날 때까지 가능한 제작과 검사는 계속한다. 어느 서비스에도 가입/연결하고 싶지 않으면 파일로 전달한다.

참고: Cloudflare의 임시 계정 배포는 로그인 전에 미리보기가 가능하지만 사용자 약관 동의와 60분 내 인수가 필요하다. 이를 영구 발표 링크로 사용하거나 무단 계정 생성으로 우회하지 않는다. 기본 하네스는 이 임시 흐름을 자동 실행하지 않는다.

## 기본 배포 경로

새 정적 발표자료는 이름을 지정한 별도 Worker로 배포한다. `wrangler.json`의 `assets.directory`는 **./public**이어야 한다. 대본·검사 결과·개발 도구·키는 이 폴더 밖에 둔다. 기존 연수의 Worker 이름이나 계정 설정을 템플릿에 넣지 않는다.

배포 요청·대상 확인이 있으면 재확인 없이 검사 → dry-run → deploy → 공개 검증으로 이어간다. 공개 범위가 미정이면 아직 공개하지 않는다. 설치 동의만으로 공개 배포까지 허용된 것은 아니다.

```sh
npm run check
npm run verify
# 실제 캡처 검토 후
node harness/harness.mjs review --reviewed --note "확인한 화면과 수정 사항"
npm run deploy:check
npm run deploy
# 공개 캡처도 확인 후
node harness/harness.mjs review --public --reviewed --note "공개 화면 검토 결과"
```

하네스가 자동으로 검사 결과·소스 해시·시각 검토 일치를 확인하고, 공개 사이트의 빌드 표식과 실제 브라우저 동작을 재검사한다. 계정 연결이 안 되거나 서비스가 거부하면 실패 상태를 보고한다. 업로드 성공/공개 검사 통과/시각 검토 완료를 구분한다. 인증 오류를 반복 재시도하거나 사용자 계정 대신 제작자 계정으로 배포하지 않는다.

실시간 백엔드는 이 정적 배포기에 넣지 않는다. 사용자 지정 provider나 기존 Worker라면 해당 프로젝트의 실행 방식·데이터 보존·바인딩·마이그레이션을 확인하고 별도 릴리스 절차로 진행한다. 검사 게이트를 무력화하지 말고 동등한 실제 증거를 남긴다.
